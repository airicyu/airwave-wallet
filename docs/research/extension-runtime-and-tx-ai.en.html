Chrome extension runtime and transaction-AI isolation

Airwave is a Manifest V3 Solana wallet. Each surface is its own Chrome context, not one shared JS heap. Signing analysis runs in manifest.sandbox. Models, RPC, keys, and grading live only in the service worker.

1. Eight isolated runtimes

Variables, closures, and React stores do not cross contexts. The page world has no chrome.*. The sandbox has neither privileged extension APIs nor network. The only business hub is the service worker.

dApp page

A normal website. It sees Wallet Standard only, not the extension interior.

page world

inject.ts

Injected into the main world by the content script. Registers Airwave Wallet Standard and leaves the page via postMessage.

no chrome.*

content-script.ts

Isolated world on the same tab. Forwards allowlisted dapp.* and posts results back to the page.

has chrome.runtime

background SW

Command routing, pending, vault / signing, simulation, OpenRouter, host tools, Decisions.

sole privileged hub

popup

Toolbar wallet shell. Accounts, settings, wallet-send confirm. Destroyed when closed.

extension page

side panel

The same wallet UI. When the panel is open, dApp approval can mount as an in-shell overlay.

extension page

popout

Approval window from chrome.windows.create. Main dApp approval path when the side panel is closed.

extension page

offscreen + sandbox

Offscreen only embeds the iframe and forwards JSON. The sandbox runs the harness loop with no network and no chrome.*.

short-lived · bound to assess

What the older note missed

extension-message-flow.html described five runtimes. The current build also has a side panel, offscreen, and sandbox. Approval is no longer always a popout.

2. Who can talk to whom

There are only three channels: page ↔ content uses window.postMessage; extension pages / content / offscreen ↔ SW use chrome.runtime; offscreen ↔ sandbox uses another postMessage bound to event.source.

page postMessage chrome.runtime ↔ SW extension-page commands offscreen ↔ sandbox

3. Who holds what (state and custody)

Persistent state treats chrome.storage as truth. UI mirrors it via onChanged and commands. Pending requests and AI reports live only in SW memory. They are not written to storage and are not recovered by a lucky hydrate.

Data Where it lives Who may touch it Who must not
password-boxed vault chrome.storage.local · airwave.vault.v1 SW decrypts into memory only inject / content / sandbox / offscreen / approval pages
unlock working key SW memory + storage.session (TRUSTED_CONTEXTS) SW only; cleared when the browser closes any page world, sandbox
settings / account meta / connections storage.local SW reads and writes; extension pages see the public shape OpenRouter key is omitted from getState
pending sign request SW Map SW; UI via ui.getPending storage hydrate, content, sandbox
TxAiAssessState SW memory, keyed by that requestId SW writes; approval page short-polls not persisted, not reused across pendings
assess transaction snapshot SW session · signature slots stripped host tools hit this copy only sandbox does not get the live unsigned bytes as a mutable object; CU edits do not update the snapshot
OpenRouter API key settings secret field; full text only via the extension-page secrets command SW uses it for chat / Decisions offscreen, sandbox, public getState

How the wallet shell picks an approval surface

dApp connect / sign: if the side panel is open → uiHost: "sidebar" and notify the in-shell overlay; otherwise open a popout. The wallet’s own walletSend stays in the originating popup / sidebar and does not open a popout. Closing the popout ends that pending (walletSend / signAndSend have their own finish paths).

4. Message trust roots

Trust Chrome’s sender and event.source, not a self-reported from string in the envelope. Results go back on the originating line. There is no default all-tab broadcast.

Channel Allowed Rejected
inject → content event.source === window and matching origin; command in PAGE_COMMANDS any wallet.* / ui.*; forged off-site messages
content → SW dapp.*, debug.ping; SW takes the tab origin extension-page-only commands (isExtensionPage blocks them)
popup / sidebar / popout → SW ui.*, wallet.*, shell.* a web-page sender impersonating an extension page
offscreen → SW (airwave-tx-ai) sender.id is this extension, no tab, URL contains offscreen content / web pages / fake offscreen
SW → offscreen no tab; URL empty or contains service-worker / background other extension pages firing assess.start
sandbox ↔ offscreen only the own iframe / parent event.source page, content, unknown frames

Deliberately not done

No RSA encrypt / decrypt theater on every inject ↔ extension result. No chrome.storage event bus. No writing pending or AI reports to storage and hoping a later reopen hydrates them.

5. Transaction-AI isolation layers

The model only decides the next tool call inside the sandbox. Real network and chain work always return to the SW. Offscreen exists for one reason: a service worker cannot host a DOM iframe, so it is a short-lived host.

service worker highest privilege
  • After enqueue, if the switch is on and the key is non-empty, auto assess.start once
  • Snapshot workingTx ?? original bytes and strip signature slots
  • Open / close offscreen; run allowlisted tools; call OpenRouter chat
  • Compute deterministic flags locally; then Decisions; then the floor
  • Does not hand the key, vault, or live unsigned bytes to the sandbox
offscreen relay only
  • Creates the sandbox iframe: chrome.runtime.getURL("src/sandbox/index.html")
  • Forwards SW assess.start / assess.abort downward
  • Forwards sandbox tool / llm.chat / done / fail upward, then posts the reply back
  • Does not execute tools, hold the OpenRouter key, read settings secrets, or call Decisions
sandbox offline JS
  • CSP: sandbox allow-scripts; script-src 'self'; object-src 'none'; connect-src 'none'
  • Page also sets connect-src 'none'; the bundle is the copied agent-harness/loop.ts
  • At most 12 steps: llm.chat → optional tool → reportText
  • No chrome.*, no fetch / XHR / WebSocket, no vault, no signing, no eval of model strings
approval shell consume only
  • Mounts the single-row “AI analysis” card only when conditions match (under the title, above expected changes)
  • Short-polls ui.getPending for txAi; does not invent a second start path
  • Refresh / 3-second simulation updates expected changes only; does not rerun AI
  • A high grade never disables approve; ui.resolvePending does not wait for assess

6. AI flow for one signature request

Only signTransaction / signAndSendTransaction / walletSend. signMessage is out of scope. At most one assess at a time; a second queues; a finished pending is dropped.

01
Pending enqueues successfully

addPending fires the hook → maybeStartTxAi. An existing session does not re-enter.

SW pending → assess.ts
02
Read settings; stop if conditions fail

Continue only if txAiAnalysisEnabled and the OpenRouter key is non-empty after trim. Otherwise the approval card is omitted too.

03
Snapshot unsigned bytes

Copy workingTx ?? enqueue bytes and zero every signature slot (64 zero bytes). Later CU edits do not rerun or update this copy.

04
Ensure offscreen, send assess.start

Payload includes the locale prompt and requestId. No API key. Wall clock is 60s; each sandbox llm.chat / tool round trip is 55s.

SW → runtime → offscreen → postMessage → sandbox
05
Sandbox queries for several rounds, then assess.done

Every chat / tool hop goes through offscreen back to the SW. The SW only accepts the current activeTxAiRequestId.

06
SW local flags → Decisions → floor → done

The next ui.getPending shows the grade and report. Clicking the row card opens the overlay and does not rerun.

approval shell ← ui.getPending.txAi ← SW memory
A
Sandbox announces ready

Offscreen then flushes any queued assess.start.

B
runSandboxLoop

system + user → callModel. If the model returns tool_calls, each executeTool result is clipped to 8,000 characters and fed back.

C
llm.chat in the SW

Sanitize messages (roles, length, tool_calls cap), then call /api/v1/chat/completions with the report model from settings.

D
tool in the SW

hostToolVerdict rejects names outside the table. Args that mention write RPCs such as sendTransaction are also rejected. Tools fail if RPC is unset.

E
Stop conditions

No more tools and a non-empty body → assess.done. An empty reply gets one nudge. After 12 steps, take the last assistant body. Abort / timeout → fail.

G1
Deterministic flags trust only the SW

local-flags computes unknown_program, durable_nonce, authority_change, unlimited_approve, close_account_external, system_assign, owner_mismatch, lookup_account_unchecked on the snapshot. Flags from the model or decode_message are for the model to read and are not written into TxAiAssessState.

G2
Decisions only in the SW

POST https://openrouter.ai/api/alpha/decisions with openRouterDecisionsModel. State carries the report, SW flags, kind, and locale. No secrets.

G3
The floor only raises

unlimited_approve / authority_change / close_account_external / system_assign ≥ watch; owner_mismatch ≥ high. A failed chain read skips Decisions; the displayed grade can still be raised by the floor.

X
Drop on pending end

takePending / removePending call discardTxAi: abort, dequeue, and close offscreen if nothing else is queued. Approve does not wait.

Y
Failure still allows signing

Timeout, empty report, offscreen failing to open, or unparseable Decisions → error or UI “Unknown”. Does not block approve, simulation, or CU edits.

Z
Two simulations do not silently rewrite each other

Approval ui.simulatePendingTx uses the transaction’s own blockhash (0.32). The AI simulate tool still sets replaceRecentBlockhash: true. They share the RPC helper; the caller passes the flag.

7. The sandbox may request only these tools

There is no generic rpc(method, params). Names that mention vault / sign / storage but are not in this table are rejected. Broadcast and chain-mutating methods are hard-banned.

tool.name What the SW actually does
decode_message Decode the assess snapshot; return instructions. Its flags are for the model only
get_accounts Read-only multi-account (jsonParsed); pubkeys may be omitted and fall back to keys remembered from the last decode
simulate simulateTransaction with replaceRecentBlockhash: true and no sigVerify
rpc_get_balance getBalance
rpc_get_account_info getAccountInfo (base64 or jsonParsed)
rpc_get_multiple_accounts getMultipleAccounts, at most 20 pubkeys
rpc_get_token_accounts_by_owner getTokenAccountsByOwner
rpc_get_signatures_for_address getSignaturesForAddress, limit ≤ 20
rpc_get_transaction getTransaction
rpc_get_latest_blockhash getLatestBlockhash

Banned set

sendTransaction, sendRawTransaction, requestAirdrop, arbitrary URL fetch, filesystem, eval / new Function / dynamic import() of an unfixed URL, sandbox talking to OpenRouter directly. The host must not execute model output as code either.
