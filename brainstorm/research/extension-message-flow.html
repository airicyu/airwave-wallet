Extension Message Flow

Solana 錢包 Chrome Extension 裡，inject.js、content.js、 background.js、popup、popout 各自是獨立 runtime。這份筆記說明它們能用什麼通道通訊，以及 一次 connect / sign 的正確數據流向——對照用 storage 當 event bus 的做法。

1. 五個 Runtime

不是「同一個程式的不同檔案」，而是五份互不相通的 JS 記憶體。變數、閉包、Zustand store 都不能直接共享；只能靠訊息傳遞。

inject.js

跑在網頁主世界（page world）。註冊 Wallet Standard，給 dApp 呼叫。

無 chrome.*

content.js

同一標籤頁的隔離世界。能看 DOM，看不到網頁的 window 變數。

有 chrome.*

background.js

Service Worker。應是唯一持有密鑰、授權與簽名的地方。MV3 會被掛起。

有 chrome.*

popup

點工具列圖示開的擴充頁。管帳戶列表、設定。關掉就銷毀。

有 chrome.*

popout

chrome.windows.create 開的批准視窗。只顯示這次請求。

有 chrome.*

2. 誰能跟誰說話（通道拓撲）

真正只有兩道邊界：網頁主世界 ↔ content 只能用 window.postMessage； content / background / popup / popout 之間用 chrome.runtime。

window.postMessage（跨 page / content 世界） chrome.runtime.sendMessage（單次請求） chrome.runtime.connect（長連接 / port） 勿用 storage 當進行中操作的总线

3. 通道對照表

從 A 到 B，實際該用哪條 API。

From → To 通道 備註
inject → content window.postMessage inject 沒有 chrome.*；必須經 content 橋接
content → inject window.postMessage 回傳結果給網頁裡掛起的 Promise
content → background chrome.runtime.sendMessage 或 connect 開 port，方便長時間等批准
background → content chrome.tabs.sendMessage(tabId, …) 要帶 tabId，不要廣播所有分頁
popup / popout → background chrome.runtime.sendMessage / connect 擴充頁可直接跟 background 說話，不必繞 content
background → popup / popout port 推送，或對方主動 pull popout 也可在 URL query 帶 requestId
inject ↔ background ❌ 不直連 必須 inject → content → background
任意 → chrome.storage 持久化資料 加密私鑰、帳戶、設定；不是 request/response 通道

4. 正確流向：一次請求一條線

呼叫方發出後留下 Promise，等同一條 requestId 的回覆來 resolve。 中間不寫 operation store、不輪詢、不 rehydrate。

01
dApp 呼叫 Wallet Standard

例如 signTransaction。inject 生成 requestId，把 Promise 放進 map。

inject
02
inject → content（postMessage）

送出 command：signTx + payload + requestId + site。

inject → postMessage → content
03
content → background（sendMessage / port）

原樣轉發，附上 tabId。content 不做業務邏輯。

content → runtime → background
04
background 登記 pending，開 popout

用 Map<requestId, { resolve, tabId, port }> 記在記憶體（或 storage.session 防 SW 被殺）。開批准視窗，URL 帶 requestId。

background → windows.create → popout
05
用戶在 popout 批准 / 拒絕

popout 只顯示這次請求。Approve 時把「同意」送回 background——不要在 popout 解密私鑰。

popout → sendMessage → background
06
background 簽名

唯一持有密鑰的地方：解密 → 簽名 → 用 requestId 找到當初那條連接。

background
07
結果沿原路返回

tabs.sendMessage(tabId) → content postMessage → inject 的 Promise resolve。不要廣播所有 tab。

background → content → inject → dApp

每個 runtime 只留自己需要的狀態

inject：當前公鑰 + pending Promise map。 background：密鑰、授權、pending request。 popout：這次要給用戶看的那一條。 popup：帳戶 UI / 設定——與進行中簽名無關。 

// inject：請求與回覆用同一個 requestId 對上
const pending = new Map();

function request(command, payload) {
  const requestId = crypto.randomUUID();
  return new Promise((resolve, reject) => {
    pending.set(requestId, { resolve, reject });
    window.postMessage({ source: "solibra-inject", requestId, command, payload }, "*");
    // 可加 timeout → reject + pending.delete
  });
}

window.addEventListener("message", (e) => {
  if (e.source !== window || e.data?.source !== "solibra-content") return;
  const entry = pending.get(e.data.requestId);
  if (!entry) return;
  pending.delete(e.data.requestId);
  e.data.error ? entry.reject(e.data.error) : entry.resolve(e.data.result);
});
01
用戶在 popup 切換帳戶

popup 告訴 background「當前帳戶變成 X」。私鑰仍只在 background。

popup → background
02
background 推給已連接的 tab

只通知有連線的 origin / tab，帶上新的 publicKey。

background → tabs.sendMessage → content
03
content → inject → emit accountChanged

inject 更新公鑰並觸發 Wallet Standard 的 change / accountChanged。不要清成 null 再強制重連。

content → inject

推送，不要拉

帳戶變更是 background → 頁面的單向事件。不需要頁面輪詢 keys store， 也不需要「設 null → 再開 connect 彈窗」。

✕
把進行中操作寫進 chrome.storage

background 寫 OperationRecord → 開 popout → 指望 popout rehydrate 同一份 Zustand。這是在模擬共享記憶體。

✕
inject 用 sleep 輪詢本地欄位

單一 #operationRequestId 槽位：並行請求會互相覆蓋；timeout 靠 for-loop sleep。

✕
結果再廣播到所有 tab

popout 寫 storage + broadcast 到每個分頁。兩條通道，都不是一個 session。

✕
每個 bundle 都 import 同一套 store

為了讓狀態「看起來存在」，被迫做 syncStoreAcrossRuntime / rehydrate。指揮中心碎成五份副本。

Event bus 本身沒錯；錯的是用 storage 當 bus

Command + requestId + postMessage / sendMessage 就是正確的 event bus。結果應沿著同一條 requestId 的對話回來， 而不是寫進資料庫再讓對方掃。

5. MV3 特別注意

問題 做法
Service Worker 會被掛起 進行中請求可用 chrome.storage.session 暫存；恢復後仍用訊息把結果送回，不要讓頁面掃帳本式 storage
async listener 回傳值 onMessage 裡若非同步回覆，要 return true 並在結束時呼叫 sendResponse；長等待改用 port
找錯 tab 從 content 進來的訊息帶著 sender.tab.id；回傳時用那個 id，不要 query({ active: true }) 猜
密碼與私鑰 session 密碼放記憶體；加密後的私鑰才進 chrome.storage.local；簽名只在 background

6. 一句話心智模型

網頁只見 provider（inject）
content 只做橋
background 是唯一真相與簽名處
popup / popout 是 UI，說話對象是 background
storage 存「會活過重開」的東西
進行中的批准 = 帶 requestId 的對話，不是一份要同步的資料庫
